# MF-01 — Suíte de testes de frontend e pipeline de integração contínua

`Onda 0` · `Estimativa 8 pt` · `TODO #7` · `Depende de —`

> **Como** pessoa desenvolvedora do MarinaFlow, **quero** que backend e frontend rodem automaticamente a cada push, **para** que uma regressão em regra de negócio ou em tela seja descoberta pelo pipeline e não pelo operador da marina.

## Contexto

O backend já tem oito arquivos de teste de recurso cobrindo autenticação, convite, RBAC e os três CRUDs — é uma base boa. O frontend não tem teste nenhum: as regras de tela (visibilidade de botão por papel, filtro do histórico, máscara de telefone em `utils/phone.js`) não estão cobertas. Não existe CI: `pint` e `phpunit` dependem de alguém lembrar de rodar. As dez histórias seguintes multiplicam a superfície de regressão; esta vem primeiro.

## Contrato técnico

```
// vite.config.js — bloco de teste
test: {
    environment: 'jsdom',
    globals: true,
    setupFiles: ['./tests/js/setup.js'],
    include: ['tests/js/**/*.test.jsx'],
}

tests/js/setup.js        // @testing-library/jest-dom + stub global de route() do Ziggy
tests/js/AppLayout.test.jsx
tests/js/Historico.test.jsx
tests/js/utils/phone.test.js
.github/workflows/ci.yml // jobs: php (pint + phpunit), js (vitest + build)
```

> **Dependência aprovada em D-01:** devDependencies novas — `vitest`, `@testing-library/react`, `@testing-library/jest-dom`, `@testing-library/user-event`, `jsdom`. Ver [D-01](README.md#decisões-técnicas).

## Critérios de aceite

**AC-01.1 — A suíte de frontend roda isolada**
- **Dado** um clone limpo com `npm ci` executado
- **Quando** eu rodo `npm run test`
- **Então** os testes de componente passam sem servidor Laravel no ar e sem acesso à rede

**AC-01.2 — Regressão de papel é detectada**
- **Dado** o teste de `Embarcacoes` que afirma que o botão “Nova Embarcação” não aparece para funcionário
- **Quando** alguém remover a checagem `isAdmin` da página
- **Então** o teste falha citando o nome do botão encontrado indevidamente

**AC-01.3 — O merge é barrado**
- **Dado** um PR cujo `php artisan test` falha
- **Quando** o CI termina
- **Então** o botão de merge fica bloqueado e o job vermelho está identificado no resumo do PR

## Tarefas

1. Aprovar as devDependencies de teste com o time e registrar em D-01. _(PO + Tech lead)_
2. Instalar `vitest jsdom @testing-library/react @testing-library/jest-dom @testing-library/user-event` e adicionar os scripts `test` e `test:watch` ao `package.json`.
3. Adicionar o bloco `test` ao `vite.config.js` reaproveitando o alias `@` já configurado para `resources/js`.
4. Criar `tests/js/setup.js` com o stub de `route()` (Ziggy é global em runtime, não existe no jsdom) e o matcher do jest-dom.
5. Escrever `utils/phone.test.js` — é a unidade mais barata e valida o setup antes dos componentes.
6. Escrever os testes de `AppLayout`, `Historico` e `Embarcacoes` montando as props Inertia à mão e simulando `usePage`.
7. Criar `.github/workflows/ci.yml`: job `php` (setup-php 8.5, cache do Composer, `pint --test`, `artisan test`) e job `js` (Node 20, `npm ci`, `npm run test`, `npm run build`).
8. Acrescentar ao job `php` uma matriz de dois bancos: `services: postgres:16` com `DB_CONNECTION=pgsql`, além da execução em SQLite. Sem isso a suíte nunca vê o dialeto que roda em produção — foi assim que o `like` sensível a caixa passou despercebido. Detalhes do dialeto na [MF-02](MF-02.md).
9. Ligar a proteção de branch exigindo os dois jobs verdes. _(Tech lead)_
10. Atualizar a seção “Rodando os testes” do README com as duas suítes.
